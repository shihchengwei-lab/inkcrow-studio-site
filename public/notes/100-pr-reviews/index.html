I used Codex to review 100 open-source PRs. I left no comment on 76 of them.

It took me a while to ask what it costs someone else to answer a review comment. Codex can produce a plausible question about a few lines of code, while the maintainer getting the notification might have to write a test just to find out whether I was wrong.

I have no software engineering background. I built arc9, a review skill that guides Codex through the relevant code at a specific commit. We (me and AI) sometimes tested a finding in isolation. I usually just told Codex to start the review. It suggested what to investigate, sometimes by filling in a prompt that I sent as written. Codex also recommended whether to comment. I followed its recommendation almost every time. In a few cases, I had doubts and pushed back. I counted each primary PR once, even when we read a related PR to check the same finding.

In Kafka #24292, restoring a cache could evict an index and schedule it for deletion. If initialization then failed, shutdown canceled the deletion after the index was already gone from the map that cleanup walked. I asked who closed it and noted I hadn't run the sequence. The author reproduced it, fixed it, and added a test that fails if the evicted index stays open.

In DuckDB #29115, I described the two-row Parquet file we tested. Column x held only 1.0 and 2.0, with exact min/max bounds and no nan_count statistic. On the PR build, max(x) returned NaN with parquet_can_have_nan enabled and 2.0 with it disabled. The author reproduced it on main and opened a fix with a regression test. In Flink #30022, the author confirmed that after restoring a 2.3.0 savepoint, Flink could reuse an active event ID if the clock moved backward. Skipping occupied IDs cost about 30% in their RocksDB test, so they chose to document the behavior.

Flink #30022 comment · Flink #30022 author reply

I wanted to see whether that cost could move to recovery. We tested two prototypes against RocksDB. Both preserved the old IDs. One scanned saved state at restore time to rebuild the counters, and the other checked for occupied IDs as it assigned them. Including recovery, checking on allocation finished sooner at about 2.1 million events, while the scan finished sooner at about 4.19 million. Those were timings for our two prototypes. We hadn't measured the author's implementation. Picking one would require deciding how long a Flink job could afford to spend recovering and how much work it would do before the next restart. The maintainer had already made that call, so I kept the benchmark in my notes.

As of November 23, I had commented on 24 of the 100 PRs. On 13 of those PRs, a review point was confirmed or addressed. I was still waiting for a reply on 10, and I closed one review without confirmation. The three confirmed bugs described here, in Kafka, DuckDB, and Flink, all predated the PRs we reviewed. I didn't measure maintainer time. I did track whether the first comment gave the author enough to reproduce the problem, fix it, or decide to live with it.

The rule I ask Codex to use now is to weigh what the bug could cost against the work the author would have to do to check it. If the author would have to start from scratch, we either gather more evidence or leave the comment unwritten.
